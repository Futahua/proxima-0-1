# Open findings

Everything a review has flagged and nobody has actioned, in one place.

This file exists because of a specific failure. The first fidelity review named
nine or ten divergences; seven were sent on to be fixed, and the rest were
dropped on the floor when the findings were compressed into a work brief. One
of the dropped ones — a clamp that silently rewrote contradictory dates — came
back a day later as a visible bug, and it looked like the reviewer had missed
it. The reviewer had not missed it. The ledger had.

So: a finding goes in here the moment it is reported, and comes out only when
it is fixed or deliberately closed with a reason. Being unimportant is not a
reason to leave it unwritten.

Verified against the working tree at `148803c` unless noted. The integrity pass
below (lock snapshot, deadline expiry, timeline clipping) is not yet in a tagged
commit; it is in the working tree on top of it, and so are the timeline gesture
work (pointer-anchored zoom, grab-to-pan header, shift-drag stretch), the routing
round (hash routes, per-surface rendering, the header's restructure), slice 1 of
the data plane (the command façade, the event log, cockpit preferences), slice 2
(the service, the migration, actors and credentials) and the agent-driven round
(per-agent credentials, attribution on the record and on the card, the activity
diff, `history.revert`, and the CLI as an entry point).

## Test fixtures

`tsk_fixture_reversed` — "FIXTURE — reversed dates" — was a deliberately
contradictory task (start after deadline) left in the store on purpose, so the
invalid treatment was always visible on screen rather than only in a test. It was
labelled a fixture in its own name, because an unlabelled broken task was once
mistaken for real corruption.

**It is no longer there, and neither is anything else.** Somewhere between the
timeline-gesture round and the routing round the whole `http://127.0.0.1:4180`
localStorage bucket came up empty — every key, including the rescue key. The app
cannot do that: it contains no `removeItem` and no `clear()` (grep-verified), and
its only write path is `Store.commit()`. The likeliest cause is the browser being
restarted under a fresh profile between sessions, which is also consistent with the
stray blank tabs the shared browser was carrying. The demo data was this app's own
scratch content, not vault content — the Obsidian vault the plugin reads was never
touched — but it is gone, and it is not recoverable: the tasks' `project` links,
`order`, `weight` and `createdAt` were never written down anywhere but the store.
The fixture task in particular cannot be recreated through the app, because the
task dialog refuses a deadline that precedes its start (see Closed); it only ever
existed because it was hand-written into the store. Say the word and a replacement
set can be built through the dialogs, which is the only way it should be done.

## Closed

| Finding | How |
| --- | --- |
| **The actor was stated by the cockpit and not authenticated** (#29, #31) — any client could claim to be anyone, and an agent was indistinguishable from the human at the protocol level | The actor is now resolved from the CREDENTIAL and never from the envelope. Each agent gets its own token file (`<home>/agents/<name>.token`, 0600) minted by `POST /v1/agents`; the operator's token is its own; a cockpit holds no token at all, only an HttpOnly session cookie. `runCommand` refuses `ACTOR_MISMATCH` when the envelope claims a different actor, naming both (`{claimed:"human:minh", actual:"agent:scout"}`). The client label is still the caller's to choose for a session — it says which window, not who. Verified by driving: a command sent as `human:minh` over scout's token was refused and nothing was written; the same command over scout's own token was recorded as `agent:scout` in the log, in `list`, and on the task's card. A token is read from a file and never passed on a command line, because a command line is visible in the process table |
| **`history.revert` was named in the vocabulary and not served** (#28, the second half) | Served, and it is the safety net the frictionless decision requires: events are selected by actor and time window, compensated **per event in reverse order** (not per record — two agent edits to one field in a row are the normal case, and stopping after the newest leaves the older one in place), and **refused rather than stamped** when somebody else has changed *the same field* since. Deletes are recoverable because `task.delete` keeps the whole record. `dryRun` returns the same report without writing, so the cockpit's confirmation is produced by the code that does the work. Verified by driving: a four-step agent chain (create → two patches of the same field → move) compensated all four in reverse and the created task disappeared with them; a human edit to a *different* field did not block the agent's field being put back; a human edit to the *same* field refused and the human's value survived; an agent-deleted task came back with the same id, `createdAt` and unknown fields; and 12 events across five records produced 7 compensations and 1 refusal in one pass. `proposal.accept` remains refused, now permanently: the creator chose frictionless, so there is no queue to accept into |
| **The log and the idempotency memory were bounded in the browser** (#27) — `EVENT_MEMORY`/`COMMAND_MEMORY` trimmed oldest-first, so a replay older than the window could not be answered | Gone with the transport. | **A failed write reported success** — in-memory state moved ahead of durable state and the reader saw a normal save | One mechanism, `commit()`, wraps every mutation: snapshot, apply, and roll the whole state back if the write fails.
